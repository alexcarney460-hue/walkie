# Windows enrollment contract (lane 4 → join page lane 5)

The Windows path needs no paid signing service. The join page offers **Copy installer** and downloads one private, short-lived JSON handoff named `walkie-enroll.json` into the current Windows user's Downloads directory. It then copies the output of `bun scripts/windows/command.ts` as the one PowerShell paste. The copied command contains the inline, fixed `stage0.ps1` as UTF-16LE `-EncodedCommand`; it contains **no invite**. Lane 5 must ensure a prior download was replaced, not browser-renamed to `walkie-enroll (1).json`; otherwise show a clear local-file error and do not claim the copy action succeeded. The page must not put the invite in a URL path/query, fetched script URL, PowerShell argument, or log. A browser download and local clipboard/history can expose the handoff; display that exposure beside the action. The handoff file is removed after the bootstrap encrypts its journal, and on terminal success/failure.

The handoff JSON has these fields:

```json
{
  "code": "wk1<private bearer>",
  "release": "v0.2.0-pre.N",
  "team": "<16 lowercase hex, decoded from invite bytes 1..8>",
  "distro": "Ubuntu",
  "user": "<named Ubuntu user, ASCII letter then up to 31 letters/digits/_/->",
  "owner": "<owner handle>",
  "launchers": ["@owner"],
  "maxSeats": 4,
  "profile": "developer-worker",
  "acSleepNever": false,
  "ownerSsh": "<optional: the owner's signed SSH authorization from the link's &ssh= field, base64url, at most 1200 characters>"
}
```

The team and expiry decoded from the invite are **advisory preflight**. The roster authority validates the invite signature, one-use state, role, and team during `walkie join --invite-stdin`. The bootstrap checks the joined daemon's actual team ID afterward. The page must present the same owner, launcher set, seat cap, profile and AC power choice that it writes to the handoff; the bootstrap repeats them in its one explicit consent prompt. `acSleepNever` can be `true` only if that effect was shown in the page's consent. A company machine uses same-user seats; owner provisioning and account leases are subsequent lanes, so enrollment completion is not Ready.

`ownerSsh` is optional and is the packet the owner's add-machine link carries after `&ssh=`. The page copies it from the fragment into this handoff only (never a URL query, a PowerShell argument or a log) and, when present, shows in the same consent that the owner, their everyday agents and WalkieTalkie may sign in to the Ubuntu over SSH as the person's user. The bootstrap drops a malformed one before the consent (`^[A-Za-z0-9_-]{1,1200}$`) and says so. A carried packet is held DPAPI-protected in the journal like the code, and removed after use. Inside the one elevation, after join admission and before seats, the bootstrap runs, as WSL root with no sudo, `walkie provision root-marker install /home/<user>/.walkie ssh-linux` (the root-owned marker, then the loopback-only SSH service embedded in the binary), then, as the Ubuntu user, `walkie provision grant-bootstrap` with one JSON object on stdin (the owner node and handle, launchers, seat cap, profile, the invite's id and the packet) to record the person's consent with the packet in the same request, then `walkie ssh status --wait --json`. SSH is reported ready only when that says so; otherwise the bootstrap prints why and what fixes it, and the rest of the enrollment is kept. When the WSL step left SSH out of the consent it recorded (an SSH server that is not Walkie's already answers in the Ubuntu, or the authorization does not fit this enrollment) the status can only say that no authorization is recorded, so the bootstrap prints the WSL step's own sentence (read from that command's standard error) as the reason instead of the status's fix. A link without `ownerSsh` behaves exactly as before: no marker, no grant, no SSH service.

`stage0.ps1` fetches a versioned GitHub release over HTTPS and verifies the ECDSA P-256 signature on `SHA256SUMS` using Walkie's pinned release key. It then checks the signed release tag and hashes of `walkie-windows-bootstrap.ps1`, `walkie-windows-stage0.ps1` and `install.sh` before running the bootstrap. `scripts/release.sh` and `.github/workflows/release.yml` include all three assets in the signed manifest. The UAC process and next-sign-in task embed the fixed stage-zero verifier as `-EncodedCommand`; each invocation fetches and verifies fresh signed payload bytes before running them. The Linux installer independently verifies the signed Linux binary and signed release tag. No downloaded script is executed before verification.

The bootstrap saves only a DPAPI CurrentUser-encrypted code in `%LOCALAPPDATA%\WalkieEnroll\active\journal.json`, never the plaintext. It requires the current Windows account to be an Administrators member before consent; a different administrator entering credentials cannot decrypt the journal. The elevated process checks an existing Ubuntu for Walkie state before host changes, then enables WSL features, configures Ubuntu/systemd/linger, the `.wslconfig` idle timeout, a logon keep-alive task, and optionally AC sleep. It records a one-shot high-integrity resume task before reboot and removes it and the encrypted code on terminal failure. Immediately after confirmed join admission it clears the code from the journal, so seat setup can resume without it. The WSL CLI receives the invite on stdin. It never appears in process arguments.

The signed bootstrap installs only `curl`, `openssl`, `ca-certificates`, and `python3`. Normal installation refreshes only Ubuntu archive and security sources through a temporary source list, a separate package-list cache, and Ubuntu's default archive keyring. It does not refresh or install from configured third-party sources, and it adds no persistent repository. Before installation, `apt-cache policy` uses the refreshed isolated metadata to require an official Ubuntu candidate and checks existing local metadata for any extra source offering a bootstrap package, including one with negative priority. An extra source absent from local metadata is not covered by that check; the isolated install still excludes it. If the check refuses, the person can explicitly type `ALLOW-EXTRA-APT-SOURCES` to use the WSL instance's configured APT sources and keys; the bootstrap explains the third-party-code risk before that choice. It records installed versions in the active journal and then in `%LOCALAPPDATA%\WalkieEnroll\receipts\packages.json`. `walkie seats doctor` reports those versions; the receipt records enrollment state, not current package state. The orchestrator accepted current Ubuntu archive versions at enrollment time rather than exact pins in the signed release, so Ubuntu security updates can apply. Exact pins can also fail when Ubuntu removes superseded builds from its archive.

No Windows execution was possible in this Mac worktree. A fresh throwaway Windows + Ubuntu machine must prove first-enable reboot, same-account UAC, logon resume, idle, sign-out/sign-in, battery/AC and an owner smoke seat before this path is released. A real provider/account Ready claim belongs to the integrated acceptance lane.
